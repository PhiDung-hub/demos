❯ wat --about

WAT (What A Terminal, or Wezterm with an Agentic Tweak) runs many Claude Code and Codex sessions from one keyboard-driven WezTerm screen. I use it daily.

❯ wat features
✓fleetTracks every session: plans, sub-agents, tokens/s, context, CPU and RAM.
✓co-workingShows the messages sessions send each other, in both conversations.
✓changesDiffs each session's edits live against git; ● marks the files that session changed.
✓live grepSearches every session's conversation at once, with fff-style keys; stored decisions too.
✓decisionsGathers agent questions in one inbox with their context and each option's evidence; logs every pick; holds dangerous tool calls for approval.
✓pluginsShips a Claude Code plugin, Jev prompt review and a config installer.
✓verifyThe verify plugin: agents prove their work with end-to-end runs, cross-agent grading and Lean 4 proofs.

The video uses synthetic test sessions; the source stays private.

❯ wat plugin verify --about

verify is WAT's verification plugin. It follows How the Claude Code team thinks about verification: agents prove their work with evidence, so I review evidence instead of reading every diff, and more agents can run at once.

❯ verify --principles
✓run itThe verify-agent-os skill boots the real binary in a private tmux server with a fake fleet, drives it like the operator and captures the screen as proof. Every external program is a logging stub.guide: verification means running the change
✓graderverify run has the opposite agent grade each rubric criterion: Claude grades Codex and Codex grades Claude. A quote missing from the answer makes the verdict uncertain.guide: a separate grader checks the work against a rubric
✓outcomesVersion 2 suites run command and file checks on the produced workspace in a scratch copy. Outcome agreement never uses a model verdict.guide: end-to-end checks are hard to fool
✓invariantsLean 4 proves 104 theorems about WAT's core: usage maxima are idempotent and commutative, cleanup stays inside its root, one failure gets one recovery.guide: properties that can't break
✓out of reachA run pins its suite's fingerprint, so a suite edited after the preview exits 1 before any model call. 44 reviewed source files are pinned by sha256.guide: changes can't modify their own checks
✓benchverify bench scores the graders against labelled outcomes, and three deliberately broken Lean models must be rejected.guide: test your checks
✓missesA proof showed plan-ack checked parent steps only. An end-to-end assertion on the real binary failed before the fix and now guards it.guide: turn misses into rules
!humanMissing, skipped and uncertain checks stay in the score. A ship recommendation needs every selected check to pass; a held tool call waits in the decision inbox.guide: failing checks require human attention
❯ verify lean --results wat
✓accountingUsage maxima are idempotent, commutative, associative and monotone; work saturates at u64; fresh input never goes negative.proved · 11
✓planA live plan is acknowledged only when every parent and child step finishes.proved · 5
✓documentsAnother session cannot update a stamped document; escaped text cannot open an HTML tag.proved · 9
✓render cacheA hit reuses the exact output, retained bytes stay bounded, and selection and zoom skip Chrome and full decodes.proved · 32
✓safetyCleanup stays strictly inside its allowed root; a stale or closed session cannot authorize recovery; one failure gets at most one recovery attempt; drafts are never pasted over.proved · 47
❯ verify lean --rules
✓passesThe kernel accepts the file, and every theorem depends only on propext, Quot.sound or Classical.choice.
✗refusedsorry, admit, custom axioms, an empty audit, a timeout or unrecognized output. Any of these leaves the proof unconfirmed.
✓sandboxRuns in a copied workspace with a private home, a 30 s limit and bounded output. It installs nothing automatically.
✓enginesA suite check can also call kani or verus; each result counts only for its declared scope and assumptions.
❯ dashboard/verification/workflows.sh
✓contractsAll 104 theorems pass, and every reviewed source still matches its pinned sha256.
✓negativesThree broken safety models must fail; the gate fails if Lean accepts one.
✓gateFormatting, lint, integration and end-to-end flows and the release build. Green input hashes are recorded, so unchanged checks are skipped.
✓entry pointEach model is checked again through the shipped binary's own verify lean.

verify ships inside the WAT binary; its Eval page is unlisted, so the CLI is the entry point. Grades are model judgments over the supplied answer. Proofs cover explicit models, and source hashes guard their link to the code; they do not prove the compiler, IO or the parsers.

❯ hyperliquid-terminal --about

A Hyperliquid perps terminal (shown with live market data and a demo account; no real orders are sent) with a blazing-fast live connection, hotkey-powered execution and a local AI companion.

✓hotkeysExecutes market, limit, scale, chase, stop/take and TP/SL orders from hotkeys. Every load starts disarmed; ` arms the keys, and orders queue per coin in press order.
✓limitsA warm reload costs 20 rate-limit weight instead of 348, measured against live HL. An order whose send times out or hits a 429 stays unknown, not failed, and is checked by its client order ID.
✓ai mcpAny MCP client (Claude Code, Codex and others) reads the chart, draws levels, coaches and stages tickets you send yourself.
✓igAlso trades IG CFDs from the same screen: streaming prices, limit, stop and scale orders, draggable stop and limit lines, and the Co-pilot.
